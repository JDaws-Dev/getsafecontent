# SafeSpark Migration Safety Plan

Goal: when SafeSpark moves to the `safecontent` monorepo and swaps from
Clerk to `@convex-dev/auth`, **no kid loses a single project, share
link, version, or family-code session**.

## Snapshot

A full prod snapshot lives at `backups/prod-YYYYMMDD-HHMMSS.json`,
generated by `npx convex run safespark:exportAll '{}'` against the prod
deployment. Run `python3 -c "import json; print(json.load(open('<file>'))['counts'])"`
on the file to confirm row counts before any migration step.

**Most recent snapshot** (2026-05-27 11:04): 22 projects · 87 versions ·
10 shares · 114 requests · 3 usage · 1 family · 1 kid profile · 2 users.

## What's OK to change

- Convex `users._id` values (internal IDs) — but every reference to
  them must be remapped consistently.
- `users.clerkUserId` strings — replace with the new Convex Auth
  user identity, store the old string in `users.legacyClerkUserId`
  for one release cycle as a fallback.
- The Clerk env vars themselves — remove after migration.

## Migration recipe (when monorepo move happens)

1. **Freeze writes.** Put SafeSpark in maintenance mode on Vercel
   (or set a banner). 5-15 min window.
2. **Final snapshot.** `npx convex run safespark:exportAll '{}'`
   → `backups/prod-pre-migration.json`. Verify counts.
3. **Provision target.** Stand up the new Convex deployment under
   the monorepo. Deploy the new schema (Convex Auth + SafeSpark
   tables with `legacyClerkUserId` column on `users`).
4. **Run migration script.** A one-shot internal mutation that:
   - For each Clerk user in the snapshot: create the new Convex
     Auth user, store the old `clerkUserId` in `legacyClerkUserId`,
     map OLD → NEW user ID.
   - For Jace specifically: create a stub Convex Auth user
     (`soonerjace@gmail.com`, no password set — he'll do password
     reset on first sign-in). Map his old Clerk subject to the new
     user ID.
   - For each kid profile: keep the kid profile `_id` unchanged
     (it's the synthetic owner key on projects), update
     `parentUserId` to the new user ID.
   - For each project / version / request / usage / error / share:
     remap `clerkUserId` from Clerk subject string to the new user's
     Convex ID. Preserve `kid:<kidProfileId>` synthetic ownership
     unchanged.
   - For shares: shortIds MUST stay identical. The URL contract is
     external.
   - For kidSessions: tokens stay identical so kids on devices
     don't have to re-`/start`.
5. **Verification queries.** Run a verification script that:
   - Counts all rows on the new deployment match the snapshot.
   - For each share shortId in the snapshot, fetches it on the new
     deployment and confirms HTML byte-equality.
   - Lists every project's owner and confirms it resolves to a
     valid user / kid profile.
6. **Cutover.** Switch `NEXT_PUBLIC_CONVEX_URL` on Vercel to the new
   deployment. Redeploy.
7. **Smoke test.** Sign in as Jeremiah, confirm /parent shows the
   family + Knox + projects. Hit each of the 10 share URLs, confirm
   200 + content. Try kid /start with code `YYKN44`.
8. **Keep the old Convex deployment running for 30 days** as
   a read-only fallback. Don't delete until we're confident.

## Rollback plan

- If anything looks wrong in steps 6-7, revert `NEXT_PUBLIC_CONVEX_URL`
  to the old prod deployment. Old Convex was untouched during
  migration (we only read from it).
- The snapshot JSON is the second line of defense — re-importable into
  any fresh Convex deployment.
- The Vercel git history is the third line of defense — we can roll
  back the front-end deployment too.
